# Discovery Notes

## Visao

### Problema
Transformar uma issue pronta em software implementado, verificado e revisado exige hoje coordenar agentes e terminais manualmente a cada rodada. A fábrica prepara o ambiente, conduz implementação e revisão independentes, executa checks e entrega conforme o modo autorizado, preservando trabalho e tornando explícitos perguntas, interrupções e efeitos incertos.

Fonte: resposta do usuário e SPEC §§1–2. Este registro consolida decisões existentes; não comprova implementação.

### Usuario principal
Operador técnico que conduz desenvolvimento a partir de issues executáveis no GitHub e usa Maestri/OMP no Windows. Cadastra ou cria projetos, configura perfis e checks, inicia uma issue ou habilita a fila Ready, acompanha resultados e responde decisões reais. A fila exige exatamente um responsável, igual à conta GitHub autenticada do controlador. A distribuição em aula exige recursos portáveis, sem diretórios pessoais.

Fonte: SPEC §§1–5 e AGENTS.md.

### Referencia
As referências funcionais são Maestri para terminais/interação, OMP para execução normal dos agentes e GitHub Issues/Projects/Git/PRs para planejamento e entrega. O sistema anterior é contexto dos problemas operacionais; Wayfinder, to-spec e to-tickets permanecem antes da fábrica na cadeia. Não há produto concorrente nem referência visual aprovada especificados. O legado Aula-IA não é base de código para esta implementação.

Fonte: SPEC §§1–3 e INTEGRACAO-MAESTRI-OMP.md §§1–4.

### Pitch
A Nova fábrica de software transforma issues executáveis do GitHub em entregas implementadas, verificadas e revisadas independentemente, usando OMP normal em terminais Maestri. O operador configura o projeto e escolhe uma issue ou habilita a fila Ready; a fábrica conduz rodadas e entrega ICR, commit local ou commit com push e PR conforme autorização, preservando trabalho, histórico e decisões humanas.

Síntese das fontes para validação pelo usuário. O pitch e este Discovery ainda não receberam confirmação nesta execução.

## Funcionalidades

### Core features
1. **Preparar projetos e trabalho:** criar scaffold nas três modalidades ou cadastrar repositório existente; configurar origem/base, GitHub Project, perfis, checks e modo; iniciar manualmente ou habilitar Ready por responsável.
2. **Conduzir implementação, checks e revisão:** clone por tentativa, versão imutável no Git, Implementador e Revisor independentes, resultados estruturados por critério e correções dentro do limite; interação normal na TUI.
3. **Entregar e recuperar com clareza:** ICR, ICR + Commit ou ICR + Commit + PR; histórico/diff/evidências, perguntas correlacionadas, cancelamento, interrupção, nova tentativa e reconciliação de publicação sem duplicar efeitos.

Stories e critérios associados: [stories.md](stories.md). Fontes: SPEC §§3–7, 9–10; integração §§2–6.

### Integracoes
- Git/GitHub: Issues, Projects pessoais ou organizacionais acessíveis, identidade autenticada, commits, push e PR; GH CLI é o primeiro adapter GitHub.
- Maestri: início exclusivo pelo terminal-âncora, herdando e validando contexto real; terminais comuns por passagem.
- OMP: executor inicial, TUI e ferramentas nativas, regras/skills/LSP e gerenciamento normal de MCPs; provider/modelo/esforço exatos por perfil.
- Extensão mínima de resultados: execution_complete e execution_question, duráveis e vinculados; sem execution_accept ou execution_block genérico.
- Playwright MCP/Google Chrome de teste: aceite da UI; GitNexus no clone pertinente quando requerido.

Cadastro/scaffold local sem remoto é permitido. Iniciar e entregar em qualquer modo exige remoto GitHub confirmado, GitHub Project configurado e issue vinculada. O acesso às integrações não autoriza efeitos externos adicionais. Fontes: SPEC §§2–6 e integração §§2–4.

## Tecnico

### Stack
TypeScript strict, Node.js 24 LTS inicialmente, Fastify, React/Vite, SQLite com driver transacional e migrations versionadas, dependências fixadas em lockfile e produção compilada. Monólito modular com controlador/scheduler/worker assíncrono no mesmo processo; React/Vite é cliente. Módulos: projects, github, pipeline, workspaces, execution, verification, publication, storage e queries; contracts compartilhados sem IO. Vitest para decisões determinísticas; HTTP/Fastify inject e SQLite/Git temporários para contratos; integração real Maestri/OMP e Playwright MCP/Chrome para aceite.

Fonte: SPEC §§8 e 10.2. Registro da stack existente, sem iniciar decisões técnicas de fases posteriores ou escolher novas versões.

### Plataforma
Controlador e UI locais, ambiente executor inicial Windows, iniciado exclusivamente dentro do Maestri. Interface web utilizável em desktop e celular, com teclado, foco, nomes acessíveis, contraste e zoom medidos; app nativo não compõe a primeira entrega. Um host executor designado por conta e um trabalho automático ativo inicialmente; várias interfaces usam a mesma instância. Acesso de outra máquina depende de conexão autenticada explicitamente provida; túneis e deployment remoto não são provisionados pela primeira entrega.

Fonte: SPEC §§1.2, 4.3, 8.5 e 9.

#### Governança e limites preservados

- Issue executável tem título, objetivo/escopo e critérios de aceite em lista Markdown, com IDs capturados por ocorrência quando ausentes. Mudança semântica de critérios exige decisão/nova tentativa; comentário livre não muda escopo implicitamente.
- Ready é uma fila observada, não um evento de transição. Elegibilidade automática exige issue aberta, Project/repositório corretos, Ready, um assignee igual à conta e ausência de bloqueadores abertos. Consumo durável impede repetição por polling/restart; falha/cancelamento não gera retry automático.
- Tentativa, rodada e passagem são conceitos distintos. Rodada inicial 1; padrão de duas correções, configurável de 0 a 5. Cada correção produz nova versão e revisão independente. Pergunta humana não consome correção nem bloqueia TUI.
- Cada tentativa tem clone e base SHA próprios; não se adota o checkout do operador. Captura imutável no Git precede checks e revisão. Publicação usa os bytes aprovados, sem coletar novamente o clone mutável.
- Git guarda conteúdo versionado. Persistência guarda configuração, critérios, referências Git/hashes necessários, resultados, evidências pertinentes e estado operacional; não serializa checkout, índice, ignored ou caches. Resumos são leves; diff/evidências sob demanda. AC-29 exige medidas de tamanho persistido e latência com caches volumosos.
- Aprovação técnica, publicação e limpeza são estados distintos. Efeito incerto exige reconciliação antes de repetição. Cancelar interrompe avanços e solicita parada dos recursos próprios conhecidos; não significa rollback nem parada global comprovada. Reinício torna trabalho não terminado interrupted e não restaura sessão/autoridade.
- OMP/Maestri/MCPs são componentes confiáveis usados normalmente. Não construir sandbox, ferramentas próprias de arquivos/shell, resolver MCP paralelo ou supervisão geral. Bridge mínima somente por necessidade concreta documentada.
- Fora do escopo: merge/deploy automáticos, decisões automáticas de produto, múltiplos workers/máquinas executoras da mesma conta, migração do legado, editor completo de Kanban, attach externo e adapter Eve/Vercel.

#### Sequência e comprovação

Preservada a ordem da SPEC §10.1: (1) percurso integrado manual até ICR com pergunta/cancelamento/nova tentativa; (2) publicação autorizada e reconciliação; (3) fila Ready; (4) scaffold; (5) jornadas finais, diagnóstico e inicialização/documentação. Nenhuma fatia autoriza omitir requisitos da entrega final.

Aceite futuro: AC-01–AC-29 e INT-01–INT-18, nos termos vigentes dos documentos normativos. As stories apresentam a rastreabilidade; não alteram os critérios nem os declaram satisfeitos. Compilação, tools/list, texto de conversa e evidência histórica não comprovam integração/UI. Suíte padrão sem providers ou efeitos externos implícitos; ensaios reais exigem autorização e custos conhecidos.
