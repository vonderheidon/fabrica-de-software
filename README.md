# Nova fábrica de software

Controlador local com persistência, proteção HTTP, operações consultáveis, cadastro/catálogo de projetos e configuração global/por projeto com perfis exatos e revisões imutáveis. O contrato de produto permanece em [SPEC.md](SPEC.md); a cobertura das sprints e as interfaces disponíveis estão em [SPEC_PROGRESS.md](SPEC_PROGRESS.md).

## Requisitos e instalação

Node.js **24.x** e npm. Execute os comandos na raiz deste repositório canônico, em PowerShell. As versões diretas são exatas em `package.json`; `package-lock.json` fixa a árvore resolvida. O driver SQLite inclui binário nativo para as plataformas distribuídas pelo pacote; esta execução foi validada no Windows com Node 24.20.0.

```powershell
npm ci --cache .cache/npm --no-audit --no-fund
npm run typecheck
npm run lint
npm test
npm run build
npm run test:compiled
```

No PowerShell que bloqueia scripts `.ps1`, use `npm.cmd` no lugar de `npm`. O cache explícito mantém a instalação dentro do workspace mesmo quando o ambiente define outro cache. Não é necessário instalar ferramentas globalmente nem executar setup de scaffold.

`npm test` usa Vitest em modo não interativo, Fastify inject e SQLite temporário. O setup bloqueia conexões de rede e subprocessos; não chama providers, Maestri, terminais ou GitHub. `test:compiled` usa HTTP/SSE loopback real, porta efêmera e diretório/cwd temporários. Verifica shutdown, concorrência com outro processo Node e liberação do lock depois de término abrupto do processo criado pelo próprio teste. Nenhum dos comandos executa Git/GH.

## Execução da fundação

```powershell
npm run build
npm start
```

O processo executa somente JavaScript em `dist/`. As migrations SQL são copiadas pelo build para o pacote compilado, resolvidas por `import.meta.url`. O health check técnico é `GET http://127.0.0.1:4310/api/v1/health`, com resposta `{ "status": "ok" }`. Ele verifica a conexão SQLite, sem expor configuração ou comprovar integração Maestri/OMP. Ctrl+C/SIGTERM fecha HTTP e o banco.

Estão disponíveis `POST /api/v1/session`, `GET /api/v1/operations/:operationId`, `GET /api/v1/events`, `GET /api/v1/events/stream` e as rotas de projetos/configuração descritas abaixo. O bootstrap exige Origin exato, Host configurado, `Content-Type: application/json`, `X-Factory-Client: web` e `{}`. Emite cookie HttpOnly de sessão e CSRF independente, mantidos somente em memória. Leituras operacionais/SSE exigem cookie; mutações também passam pelo controle global de JSON/Origin/CSRF. CORS permanece fechado. A sessão técnica não autentica pessoa nem concede autoridade GitHub.

O lock local é adquirido antes de abrir o banco principal e independe da porta. Usa a trava do sistema operacional sobre `<data>/controller-lock.sqlite`, separado do banco de domínio; não depende de PID, expiração ou remoção de arquivo residual. O mesmo diretório de dados identifica a instalação. Outra instalação independente não participa desse lock. Ainda não há UI, scheduler, despacho nem handshake operacional Maestri. O registro de operações será consumido pelos comandos de domínio das próximas sprints.

Limites efetivos: corpo 16 KiB; headers 8 KiB e 64 campos; 128 conexões e 128 sessões por processo; 100 requisições por socket; 60 bootstraps e 600 requisições por minuto por instância. Timeouts: conexão/headers 10 s, recebimento/handler 15 s, keep-alive 5 s e espera SQLite 5 s. Não são SLAs. O limite de sessões recusa novas entradas com 503 e preserva as existentes; não há TTL nem expulsão silenciosa. Reiniciar revoga todas as sessões.

Eventos usam páginas de 25, máximo 100, com cursor de continuação ligado à instalação/conta/filtro/ordem. O filtro inicial é `operationId`; filtros por projeto/tentativa entram com seus domínios. SSE usa `cursor` sequencial e `Last-Event-ID` prevalente, com `resync` quando a sequência não pode ser recuperada. Há 8 streams por processo, 2 por sessão, buffer de 16 KiB, polling de 1 s e duração máxima de 60 s; o cliente reconecta usando o cursor. Desconexão e revogação encerram o stream, sem efeito de negócio. `eventCursor` da página é o cursor sequencial do snapshot, distinto de `nextCursor` da paginação.

Se desejado, o Node 24 pode carregar o exemplo editado localmente com `node --env-file=.env dist/apps/controller/src/main.js`, após o build. Nunca preencha o exemplo versionado com segredos.

## Organização e evolução

Um único pacote npm evita links de workspaces no Windows. O código preserva a organização normativa: `apps/controller/src`, `packages/contracts/src` e módulos com interface pública em `index.ts`. O import privado `#contracts` resolve os schemas fonte durante o typecheck e JavaScript compilado em produção.

`npm run lint` aplica regras estáticas com a AST TypeScript: sem `any` explícito, sem supressões, sem SQL/driver fora de storage, sem imports de internos de outro módulo ou IO/runtime em contracts. É um check de arquitetura e convenções, não um formatador.

Novas migrations são SQL incrementais em `storage/migrations`, com entrada ordenada em `loadMigrations`. Não edite migrations já aplicadas: checksum divergente interrompe a abertura. O ledger, `application_id` e `user_version` devem coincidir. Falha de migration reverte schema/ledger/seed; banco desconhecido, mais novo ou corrompido é recusado, sem fallback para banco vazio.

Novas tabelas e operações entram nas sprints consumidoras. Atualize `SPEC_PROGRESS.md` em toda sprint com fontes, comandos reais, interfaces, provas e pendências.

O pipeline compõe o adapter com a persistência SQLite de tentativas/passagens/resultados; o início manual está descrito abaixo.

Consulte [composição, limites e decisão do transporte](docs/integration/maestri-omp-adapter.md). ## Consultas GitHub e inspeção de origens

As interfaces públicas são `createGitHub` em `modules/github/index.ts` e `createWorkspaces` em `modules/workspaces/index.ts`. O módulo `projects` compõe esses serviços no cadastro/configuração; não há despacho nesta sprint.

`createGitHub()` sem contexto retorna `context_unavailable`. O host autorizado fornece `context:{kind:'windows_keyring',executable,cwd}`, com caminhos absolutos para o GH instalado e diretório de execução. Essa declaração pertence à composição confiável do host, não a um body HTTP, variável de ambiente ou detecção de binário no PATH. Ela não eleva o processo nem comprova autenticação: `getIdentity()` consulta a conta efetiva. `startController({github?,git?,execution?})` permite essa composição pelo host confiável; sem argumentos, os adapters permanecem sem contexto autorizado. Não forneça esse contexto em um runtime sem acesso autorizado ao keyring. Não houve prova real de keyring neste ambiente.

Métodos: `getIdentity`, `getProjectOwner(id)`, `listRepositories`, `getRepository({owner,name})`, `resolveBranch(reference,branch)`, `listProjects({kind:'user'|'organization',login})`, `getProject(id)`, `validateProjectSelection({id,statusFieldId,statusOptionIds})`, `listProjectItems(id)` e `getIssueContext({owner,name,number})`. Retornam `{state,data,diagnostics,retryAtMs}`. Somente `complete` representa leitura integral; dados de `partial` não habilitam despacho. IDs externos são strings e não são convertidos para números. Um ID não localizado permanece ausente/inacessível: a API pode ocultar a distinção por permissão.

As consultas paginam separadamente repositórios, Projects, campos, itens, comentários, responsáveis, bloqueadores, vínculos e valores de campos. O contexto carrega comentários completos sob demanda, sem inferir critérios de aceite deles. Referências são extraídas do corpo e dos comentários; bloqueadores estruturados vêm de `blockedBy`. PRs/drafts são identificados sem execução. `assessIssueReadiness` verifica a observação atual por IDs de conta/repositório/Project/Status, responsabilidade exclusiva, issue aberta e bloqueadores; seu resultado não é uma autorização durável. Preparação e publicação futuras devem repetir as consultas.

GH recebe somente queries GraphQL fixas por JSON em stdin, sem shell ou segredos em argv. Não há login, alteração de credenciais, atribuição de responsáveis, criação de campos ou mudança de Status. Paginação inválida, referência inacessível, limite excedido e falha intermediária produzem diagnóstico. Rate limit mantém cooldown compartilhado entre consultas do adapter e respeita o maior prazo fornecido por Retry-After/reset; sem prazo utilizável, aguarda 60 s, sem repetir automaticamente. Não há cache de identidade/autoridade.

Limites técnicos: 100 objetos por página; 100 páginas por conexão; 250 chamadas e 16 MiB de respostas por operação; 4 MiB e 15 s por subprocesso. Excesso produz leitura parcial/indisponível, nunca um resultado completo truncado. São limites de recursos, não SLAs. Stderr e exceções nativas não são retornados, registrados ou persistidos; diagnósticos contêm códigos e recuperação fixos.

`createWorkspaces({github,context?})` recebe contexto Git separado `{kind:'windows_keyring',executable}`. `inspectOrigin({source:{kind:'local'|'github',location},baseBranch,remoteName?})` identifica origem por propriedades Git/URL e ID remoto, preserva a origem e retorna base SHA e pré-requisitos. Caminho local deve ser absoluto e acessível; a raiz é resolvida em runtime. HTTPS/SSH de `github.com` são aceitos; URL com credencial, query ou fragmento é recusada sem ecoar o valor. Vários remotos/URLs exigem escolha explícita, sem preferência silenciosa por `origin`. Remoto ausente permite identificar cadastro local, mas não habilita execução. Project e vínculo da issue continuam obrigatórios na preparação.

A inspeção local usa apenas `rev-parse`, `status --porcelain=v2 -z` e leitura de configuração. Desabilita refresh opcional do índice, lazy fetch, fsmonitor e prompts; remove seletores Git herdados que desviariam o cwd. Não faz fetch, stash, reset, commit ou limpeza. Base local é a branch exata em `refs/heads`; divergência de SHA remoto é informada. Mudanças dirty ficam fora da futura tentativa. A inspeção não grava SQL, checkout, índice, caches ou snapshots.

A suíte padrão usa respostas controladas e processos falsos. A fixture de filesystem compara bytes/índice/HEAD antes/depois, sem executar Git. Prova com Git temporário real, ajuda das versões instaladas e consulta GitHub real precisam do contexto autorizado com keyring; não foram executadas neste runtime. Documentação de referência: [GH API](https://cli.github.com/manual/gh_api), [GraphQL Projects](https://docs.github.com/en/graphql/reference/projects), [GraphQL Issues](https://docs.github.com/en/graphql/reference/issues) e [Git status](https://git-scm.com/docs/git-status), consultadas via Context7/documentação oficial.

## Projetos e configuração persistida

Todas as rotas abaixo usam `/api/v1`, sessão técnica e `no-store`. POST/PUT exigem JSON, Origin e CSRF, além de `Idempotency-Key` UUID criado pelo cliente. PUT exige o ETag da leitura correspondente em `If-Match`.

| Rota | Contrato |
| --- | --- |
| `GET /projects?search=&limit=&cursor=` | Resumos com identidade, origem, revisão e pré-requisitos; página de 25, máximo 100. Busca literal por nome; ordenação SQLite `NOCASE` por nome e desempate por ID. |
| `POST /projects` | `{name,source:{kind:'local'|'github',location},baseBranch}`; `201`, Location, ETag e operationId durável. Origem passa por `workspaces.inspectOrigin`. Local sem remoto é permitido. |
| `GET /projects/:projectId` | `{project,prerequisites,eventCursor}`, ETag do projeto. |
| `GET /settings` | `{settings,profiles,eventCursor}`, ETag composto de settings e todos os IDs/revisões de perfis. |
| `PUT /settings` | `{changes,profileChanges?}`; gravação única, novo ETag, operationId e receipt. |
| `GET /projects/:projectId/configuration` | `{configuration,settings,profiles,prerequisites,eventCursor}`, ETag composto também com projeto/revisão corrente. |
| `PUT /projects/:projectId/configuration` | `{projectChanges,globalChanges?,profileChanges?}`; confirma nova revisão imutável, ponteiro, globais explícitos, perfis, índice da operação e evento na mesma transação. |
| `GET /projects/:projectId/configuration-options` | `ownerId?,ownerKind?,githubProjectId?,statusFieldId?,cursor?,limit?`; Projects pessoais/organizacionais, campos/opções, perfis, completeness, diagnostics e retryAtMs. Permite consultar uma seleção ainda não salva. |

O cadastro gera UUID próprio e uma revisão inicial obrigatória, mesmo com nome/pasta repetidos. Não clona, recruta ou altera a origem. A FK composta vincula ponteiro, projeto e número de revisão; guards impedem UPDATE/DELETE do histórico. Pré-requisitos são observações/configuração, incluindo aviso de dirty excluído; preparação ainda precisa revalidar conta, remoto, issue/Project, base e executor. Consultar um Project não seleciona uma conta persistida nem concede autorização.

O cursor do catálogo vincula instalação, conta, busca e ordenação; fixa o limite superior das inclusões visíveis na primeira página. Não carrega checks, guidance, conteúdos do repositório, índice ou HEAD. O cursor de opções também vincula configuração, seleção e conjunto remoto: mudança exige recarregar a primeira página com `409 OPTIONS_CHANGED`, sem truncamento silencioso. Leitura remota parcial/indisponível é explícita.

`projectChanges` cobre origem/base, Project e owner por node ID, campo single-select e opções distintas `ready/inProgress/inReview/delivered`, perfis dos dois papéis, checks, correções, modo, automação, ordem e guidance. Mapeamento não nulo precisa ser completo, acessível e validado por `github` antes de gravar. `queueOrder` usa `{priorityFieldId:null|string,priorityDirection:'asc'|'desc',useBoardPosition:boolean}`; ordenação real da fila pertence à sprint consumidora. Checks usam `{id,command,cwdRelative,timeoutMs?}`; IDs distintos e cwd relativo sem escapes. Cada novo projeto começa com correções 2 (0–5), modo `icr` e automação desligada.

`changes/globalChanges` editam host, diretórios, `maestriSettings`, automação e defaults separados de tempo, custo e artefatos. Omissões, inclusive dentro de defaults/Maestri/queueOrder, são preservadas; listas fornecidas são substituições explícitas. `maestriSettings` aceita `formatVersion:1` e `workspaceId?` não sensível; não recebe endpoint, token ou pareamento Wire. TTL e custo não configurados mantêm seu estado próprio; zero configurado é preservado. Artefatos mantêm `automaticDeletion:false`.

Diretórios informados são resolvidos relativamente ao diretório de dados do bootstrap ou como absolutos, canonicalizados e conferidos como diretórios locais acessíveis para leitura/escrita; erro não confirma gravação. `dataRoot` é a escolha persistida: alterá-la não move o SQLite já aberto. `FACTORY_DATA_DIR` continua definindo a localização efetiva do banco deste processo. Esta sprint não implementa a migração física de uma instalação entre diretórios; trocar o bootstrap isoladamente não transporta os registros existentes.

`profileChanges` é uma lista de perfis completos `{id?,name,executor:'maestri-omp',provider,model,effort,guidance}`. ID ausente cria um perfil com UUID do servidor; ID existente edita por CAS, sem resetar os demais. ID desconhecido recebe 404; duplicado recebe 400; capacidade total 100. Valores são preservados exatamente, sem provider/modelo/esforço demonstrativos ou fallback. Selecione perfis pelos IDs retornados. Não há exclusão de perfil referenciado.

ETags são opacos. Ausência gera 428; revisão alterada gera 412; chave reutilizada com conteúdo/precondição/escopo diferentes gera 409. Repetição idêntica recupera o recibo antes de CAS, validação remota ou acesso a diretórios; a resposta inclui a leitura atual do mesmo recurso e o recibo original. Comando sem mudança efetiva retorna `409 NO_CHANGES`. Nenhuma falha parcial retorna Salvo; revise a edição no cliente e reaplique sobre a leitura atual. O shell web já está conectado às leituras existentes; formulários de edição e os fluxos de domínio restantes ainda não estão disponíveis.

Interface de serviço: `createProjects({storage,github,workspaces,directoryBase})`, em `modules/projects/index.ts`, oferece `registerProject/listProjects/getProject/getSettings/saveSettings/getConfiguration/saveConfiguration/getConfigurationOptions`. IO remoto/filesystem antecede SQL. `storage` expõe leituras editáveis `{view,etag}`, gravações tipadas e recuperação idempotente; não oferece conexão/transação pública. TypeBox e tipos estão em `packages/contracts/src/projects.ts`, reexportados por `#contracts`; schemas comuns ficam em `base.ts`.

Provas locais incluem SQLite real, HTTP inject, rollback em cada ponto da gravação agregada, duas abas, corrida durante IO, idempotência, histórico e migração real 2→3. O smoke compilado exercita settings/CAS/idempotência e catálogo por HTTP loopback real, além de SSE/shutdown/lock. Neste sandbox, `realpath` retorna EPERM inclusive para o workspace; a prova positiva controla somente essa resolução e usa `stat/access` reais. Produção mantém a canonicalização real e falha segura, sem fallback ou alteração de ACL. Cadastro/opções com Git/GH reais e resolução canônica completa continuam sem prova neste runtime.

## Scaffold e criação somente local

O backend oferece catálogo versionado, plano sem efeitos e criação local. As rotas usam sessão técnica; os POSTs exigem JSON, Origin e CSRF. A criação exige também `Idempotency-Key` UUID. Não há criação remota ou push nesta fatia.

| Rota | Contrato |
| --- | --- |
| `GET /api/v1/scaffold/options` | Identidade/versão/digest do catálogo, templates/digests/resumo de engenharia, raiz configurada, observação de conta, modalidades e capacidades/pré-requisitos atuais. |
| `POST /api/v1/scaffold/plans` | `{name,templateId,templateDigest,destinationRelative,creationMode:'local',baseBranch,triageEnabled}`; retorna `{planHash,plan,prerequisites}` sem criar diretório, Git ou remoto e sem gravar plano no banco. |
| `POST /api/v1/scaffold/creations` | `{planHash,plan,authorized:true}`; revalida o plano completo e confirma intenção/creationId/operação/evento antes de agendar arquivos/Git. Retorna `202 OperationAccepted`, com `resource:{type:'creation',id}` e Location da operação. |
| `GET /api/v1/scaffold/creations/:creationId` | Criação, pasta canônica, branch, baseline SHA/ref, projectId, etapas confirmadas/pendentes, diagnóstico, pré-requisitos e ETag. Não executa efeitos ou inspeciona conteúdo de arquivos. |

Configure `projectsRoot` em settings. O destino é relativo a essa raiz e seu pai deve existir; o destino final deve ser novo. Caminhos absolutos, escapes, nomes Windows reservados, links/junctions e alteração de identidade dos diretórios são recusados. O plano vincula instalação, ETag agregado de configuração, conta observada, template, metadados dos arquivos, branch, engenharia, destino e efeitos. Mudança inicial exige outro plano; não há assinatura de autoridade permanente. Mesmo sem contexto Git é possível planejar, com o pré-requisito explícito; criar exige o contexto confiável de `startController({git,...})`, que não pode vir de HTTP ou ambiente.

`resources/templates` contém o catálogo e os textos de engenharia; o build os distribui em `dist/resources/templates`, resolvidos por `import.meta.url`. Não dependem de skills pessoais. O template gera tracker GitHub, regras de consumo de glossário/ADRs e apontadores em `AGENTS.md`, preservando instruções e seções existentes do template, inclusive quando há `CLAUDE.md`. `triageEnabled` representa a escolha de usar a skill de triagem já disponível no ambiente dos agentes; habilite somente quando aplicável. A escolha inclui o vocabulário e seu apontador no plano. Nenhuma skill ou label é instalada/criada. `.gitignore` exclui credenciais conhecidas e saídas geradas e conserva exemplos `.env*.example`; isso não é um scanner universal de segredos.

O destino é reservado exclusivamente. Etapas directory/files/git/baseline são registradas antes/depois; baseline usa `chore: initialize project`, identidade técnica `Factory <factory@localhost>`, branch escolhida, hooks/templates vazios e configuração Git global/sistema desabilitada para essa operação. SHA, ref, ausência de parent e estado limpo são conferidos antes do cadastro. Cadastro e conclusão são atômicos e usam a mesma branch; remoto/Project ficam ausentes, automação desligada e nenhum agente ou issue é iniciado. Somente esse novo destino recebe as operações Git do scaffold.

Falha conserva arquivos, Git, baseline conhecido e etapas anteriores. Uma etapa cujo resultado não pôde ser gravado permanece incerta; replay recupera o recibo e não repete criação. Reinício diagnostica intenções incompletas e não retoma efeitos. Inspecione a criação por ID; não há rollback destrutivo, readopção de pasta ou retry automático. Há no máximo oito criações acompanhadas por processo. SQL guarda plano por metadados, referências e estado, sem bytes do template/projeto, índice, caches ou cópias de checkout. Efeitos locais usam `creation_steps`; o journal remoto existente continua restrito aos seus tipos/autorização.

As provas desta fatia usam filesystem, SQLite e HTTP inject reais, com Git/canonicalização controlados. Não houve criação de baseline por um Git real nem prova integral AC-02/05 no host autorizado.

## Cliente web

`npm run build` compila o controlador e o cliente React 18 para `dist/web`. O controlador serve essa pasta na mesma origem loopback; a página abre na Principal e não oferece formulário ou sessão humana. Os únicos destinos internos são `#principal/dashboard`, `#principal/projetos`, `#principal/fila`, `#principal/tentativas`, `#principal/registros` e `#principal/configuracao`; `#login` é normalizado para a Principal. Parâmetros permitidos guardam contexto de leitura e identificadores, não segredos ou rascunhos.

`apps/web/src/api/http.ts` serializa `POST /api/v1/session`, conserva CSRF somente na memória do módulo e usa caminhos relativos. Um `401` em leitura permite um bootstrap e uma nova leitura; um `401` após comando só renova a sessão e não repete o comando. `403` mantém diagnóstico visível, sem CORS ou bootstrap em loop. `AppShell` mantém um diálogo acessível compartilhado, com foco inicial, contenção de Tab, fundo inerte, Escape e retorno do foco. O dashboard, projetos, configurações e registros consultam rotas existentes; fila e tentativas exibem disponibilidade explícita até existirem contratos de leitura.

A composição e os tokens visuais seguem `docs/Docs20261016_073031/design/artifact.html` e `design-contract.json`: grafite/branco/laranja, seis destinos, breakpoints 950/650 px e densidade aprovada. Não houve inspeção visual automatizada nesta sprint; o build comprova a compilação e empacotamento, não o aceite visual Playwright/Chrome.

## Preparação de issue e ambiente independente

As rotas usam a proteção HTTP comum, sem iniciar processos. `POST/PUT` exigem `Idempotency-Key` e PUT também exige `If-Match` do GET da preparação.

| Rota | Comportamento |
| --- | --- |
| `GET /api/v1/projects/:projectId/issues?search=&limit=&cursor=` | Itens do Project configurado, com tipo, motivos e completude. PR/draft não são issues executáveis. O cursor vincula conta, instalação, configuração, busca e conjunto observado; mudança exige recarregar a primeira página. |

Overrides aceitam `baseBranch`, `implementerProfile`, `reviewerProfile`, `checks`, `correctionLimit`, `timeDefaults`, `costDefaults` e `artifactPolicy`. Perfil aceita `{kind:'reference',id,revision}` exatos ou `{kind:'value',profile}` completo. Defaults não são alterados. Configuração/perfis são materializados por valor no preview; TTL/custo ausentes e zero configurado conservam seus estados. Guidance efetiva combina projeto e preparação. Alterar configuração do projeto requer salvar novamente a preparação para vincular a revisão atual.

O parser público `interpretIssue({title,body})`, em `pipeline/index.ts`, aceita seções Markdown `Critérios de aceite`/`Acceptance criteria` com listas, checkboxes opcionais e IDs `ac-N`. IDs explícitos são únicos sem distinção de maiúsculas; IDs gerados reservam todos os explícitos e seguem as ocorrências. Textos iguais permanecem critérios distintos. Comentários livres, exemplos em fences e comentários HTML não introduzem critérios. Título, objetivo/escopo e lista válida são obrigatórios; erro não produz um conjunto truncado executável. `github.getIssueContextById(id)` confere identidade antes e depois da consulta completa.

`createPreparations({storage,github,workspaces})` e seu tipo são públicos em `projects/index.ts`. Oferece `listIssues`, `createPreparation`, `getPreparation`, `updatePreparation` e `revalidateSummary({preparationId,preparationRevision,authorizedSummaryHash})`. A revalidação relê a observação e recusa mudança material com `409 SUMMARY_CHANGED`; alterações da preparação/configuração durante IO recebem 412. Qualquer save muda revisão/hash. O hash inclui issue/objetivo/critérios/referências/dependências, conta, base fixa, configuração efetiva, modo e efeitos. A revalidação não aceita início, não persiste autoridade e não substitui o gate transacional da futura sprint de tentativas.

Preparações persistem escolhas e seu histórico imutável, operação e evento. `storage.getPreparation/recoverPreparationCommand/savePreparation` não expõem SQL. Repetições recuperam a operação antes de CAS/validação de escrita e retornam o recurso atual com recibo original; montar a resposta atual consulta novamente os previews remotos. `GET /operations/:operationId` permite recuperar o recibo mesmo se a consulta remota do preview falhar após o commit. `previousAttemptId` ainda retorna 404: nenhum vínculo com tentativa inexistente é aceito antes da sprint consumidora.

`createWorkspaces({github,context?,dataDirectory?}).prepareAttempt({attemptId,issueNumber,source,baseSha})` prepara `<data>/work/<attemptId>/implementation` e branch `factory/<issueNumber>/<attemptId>`. O diretório de dados vem da composição confiável; o input não escolhe o destino. Exige contexto autorizado, ID UUID, SHA completo e pasta de tentativa nova. Clona com `--no-local --no-hardlinks --no-checkout`, sem shared/reference/alternates, e faz checkout da SHA fornecida somente no clone próprio. A origem recebe apenas leitura de raiz/commit, sem importar dirty. Hooks/templates do clone ficam desabilitados; gitdir/worktree são explícitos. Alternates, clone shallow, submodules, filtros de conteúdo e symlinks não suportados no Windows geram diagnóstico. Falha devolve recurso, ownership, base/branch e código sanitizado; preserva o recurso parcial e não adota uma pasta existente. Retentativa de uma execução usará outro ID.

O preview informa `canStart:false`: consultar/salvar uma preparação não concede autoridade nem inicia clone/processo. O comando de início abaixo revalida o resumo e persiste a intenção antes dos efeitos. As provas locais usam SQLite/HTTP inject reais e Git/GitHub/canonicalização controlados; clone Git real e integração Maestri/OMP continuam sem prova no runtime atual.

## Início manual e resultado oficial durável

`POST /api/v1/attempts` recebe `{preparationId,preparationRevision,authorizedSummaryHash,authorized:true}`, `If-Match` da preparação e `Idempotency-Key` UUID. Exige sessão, Origin e CSRF. Retorna `202 OperationAccepted`, com `resource:{type:'attempt',id}`, recibo durável e `Location` de `/api/v1/operations/:operationId`, antes de aguardar clone/handshake. `GET /api/v1/attempts/:attemptId` retorna resumo leve com ETag: fase, suspensão, resultado, tracking, passagem/rodada inicial, diagnóstico, revisão, cursor e recibo do resultado. Não carrega captura ou evidências completas.

`createPipeline({storage,preparations,execution,workspaces,observeTools,hostName?,logFailure})` é a composição pública em `pipeline/index.ts`. `startAttempt` refaz a observação de conta, issue aberta, assignee exclusivo, Ready, Project/owner/vínculo/Status, bloqueadores, remoto e base em todos os modos; exige o host designado. A transação IMMEDIATE repete CAS/configuração, deduplica por conta/repositório/issue e grava operação/recibo, tentativa, critérios, rodada 1, passagem implementadora e recursos planejados. IO externo ocorre antes ou depois dessa transação. Uma chave idêntica recupera o recibo antes de novas consultas ou efeitos; chave divergente retorna 409. Concorrência por issue retorna `ATTEMPT_ACTIVE` com referência à tentativa do escopo válido, inclusive entre cadastros duplicados. Início manual já consumido exige uma futura ação explícita de nova tentativa; não reinicia após falha/restart.

`AttemptCapture` (`formatVersion:1`) preserva por tentativa `preparationId/preparationRevision`, `summaryHash`, `accountId`, contexto completo da issue, `baseSha`, `configuration` efetiva com `origins`, critérios por identidade e `criteriaDigest`. `roleResources` captura ambos os papéis com `id/role/version/path/sha256`. `tools` contém uma observação própria para `node/git/gh/maestri/omp`: `state/version/cause/affectedRequirements/observedAtMs`. Versão indisponível é `null`, com causa e requisitos pendentes; a tentativa fica suspensa por `TOOL_VERSION_UNAVAILABLE`, sem clone/provider. Contrato obrigatório ausente/ inválido impede despacho. Não há preflight pago, conteúdo de checkout, índice, cache ou transcript na captura.

Após o commit, o pipeline registra o início do ambiente e chama `prepareAttempt` com identidade e SHA capturadas. Confirma ownership/falha no journal, preserva recurso parcial e revalida autoridade/resumo antes de chamar `startPassage`. O port `storage.executionPersistence()` reserva somente a passagem e terminal já vinculados à tentativa. O handshake confirma perfil e versão OMP observados em campos próprios da passagem, sem sobrescrever a captura inicial. Defaults ou recursos alterados não reescrevem capturas anteriores. Cancelamento durante clone conserva o recurso retornado e impede despacho posterior.

`ExecutionPersistence.acceptResult` aceita somente schema do papel, vínculo exato e todos os criterionIds capturados, únicos e com evidência/veredito. Grava hash canônico, UUID de recibo, resumo, resultados por critério, fase e eventos na mesma transação; só então o canal privado envia ACK. Repetição idêntica recebe o mesmo recibo, inclusive após reopen; outro hash conflita. Payload inválido, SQL busy ou falha em qualquer escrita não ocupa resultado/recibo e permite corrigir/repetir o payload. Resultado implementador move para `verifying`, mantendo resultado final nulo; declaração do agente não comprova checks ou entrega. O mesmo port confirma revisão/achados/resoluções com a prova de independência descrita abaixo.

Migration 005 acrescenta tabelas STRICT `attempts`, `attempt_criteria`, `rounds`, `passages`, `resources`, `passage_results`, `criterion_results`, `passage_events` e `execution_questions`. FKs compostas impedem vínculos entre tentativas; guards preservam campos capturados, critérios, identidades e resultados aceitos. Fase, suspensão, tracking e resultado continuam eixos distintos. Pergunta pendente impede resultado; somente recibo de resposta libera sua suspensão. Restart marca tentativas incompletas como `interrupted`, preserva capturas/resultados e não restaura sessões nem agenda outro lançamento.

As provas locais incluem SQLite real, HTTP inject e adapter real com native/channel/bootstrap controlados, verificando commit antes do ACK e recuperação após falha. Git/GH, clone, TUI/provider, MCP útil e abertura nativa reais exigem host/contexto autorizados e a integração opt-in; não são comprovados por essas fixtures. Publicação, nova tentativa e UI de início/detalhe continuam nas sprints consumidoras. Captura Git, checks e revisão estão descritos abaixo.

## Versão Git imutável e repetição de captura

Aceitar o resultado oficial do Implementador agora grava também uma entrega `pending`, na mesma transação do hash/recibo/critérios. Após o commit, o pipeline reserva a captura e executa o IO. `writesStopped:true` continua obrigatório; a extensão OMP observa `tool_execution_start/end` e recusa `execution_complete` enquanto outra ferramenta estiver em execução. O Implementador deve aguardar também seus processos que continuam em background. Essa coordenação não é um supervisor de processos nem um bloqueio do filesystem. Conversa e ferramentas nativas continuam disponíveis; o contrato proíbe novas escritas de produto até uma rodada explícita de correção.

`workspaces.captureDelivery({attemptId,passageId,deliveryId,baseSha,declaredFiles})` usa somente o clone próprio. Enumera nomes Git por NUL, inspeciona bytes/modos e prepara índice temporário inicializado da base. O índice de implementação recebe somente leitura; nenhum `add`, refresh ou reset é aplicado nele. Duas observações de conteúdo/HEAD/índice/seleção, mais a conferência das leituras intermediárias, detectam alterações durante a captura. Não há vigilância contínua. Lock/conflito de índice, sparse checkout, arquivo especial/symlink, submodule, ponteiro LFS, filtro de conteúdo e incompatibilidades geram diagnóstico antes da revisão.

Objetos ficam em `<data>/git/<attemptId>.git`. Um commit técnico privado ancora a tree e tem a base como único parent; `contentIdentity` é o ID Git da tree. A ref exclusiva `refs/factory/deliveries/<deliveryId>` usa criação com precondição de ausência e nunca é sobrescrita. Ref direta, commit/tree/base e objetos são conferidos antes da confirmação e ao ler diff. O repositório não usa alternates/hardlinks para depender do ambiente removível. Esse commit técnico não é o commit de entrega, baseline de scaffold ou autorização para push. Banco e eventos guardam somente identidades, refs, hashes, diagnósticos e metadados; índice temporário é descartado também nas falhas tratadas.

Ignorados não são enumerados para coleta. Arquivos novos com nomes conhecidos de segredo (`.env` exceto modelos example/sample/template, credenciais/netrc/chaves privadas/secrets) são excluídos; um desses nomes já tracked recusa a captura. Isso é uma regra conservadora por nomes conhecidos, não um detector universal de segredos. `declaredFiles` é uma extensão opcional compatível do resultado v1: caminhos relativos declarados, sem bytes. Quando um arquivo novo declarado é ignorado ou excluído pela regra de segredos, `delivery.warnings` registra tentativa/passagem/versão, caminho e motivo. A declaração não autoriza coletar o conteúdo excluído. A sprint 017 consumirá esses metadados no detalhe.

Repetição exige a mesma passagem produtora concluída e ainda acompanhada, falha técnica e revisão atual. Estado alterado, captura simultânea, versão capturada, interrupção/cancelamento ou continuidade revogada retornam `CAPTURE_RETRY_NOT_ALLOWED`. Não recruta Implementador nem refaz clone. Resposta perdida é recuperada pelo mesmo operationId antes de verificar novas revisões; conteúdo/precondição divergentes conflitam. Cada execução técnica tem histórico em `capture_runs`. Se a ref foi criada mas o commit de metadados falhou, a repetição só a recupera se tree e base coincidirem; conteúdo diferente exige outra versão.

Limites técnicos de captura: 100.000 arquivos, 16 MiB/arquivo e 128 MiB de conteúdo total; limites existentes do subprocesso Git continuam 4 MiB de stdout/15 s por chamada. O excesso é diagnóstico, nunca entrega truncada. Patch acima de 64 KiB de blobs somados recebe `PATCH_TOO_LARGE`; patches emitidos respeitam teto de 256 KiB/página, além do limite de entradas. Binários e texto não UTF-8 são identificados sem patch corrompido.

Migration 006 acrescenta `deliveries`, `capture_runs` e `capture_warnings` STRICT, FKs compostas e guards de identidade/conteúdo/histórico. Resultados anteriores são preservados com entrega identificável e continuidade revogada; migration/restart não restauram autoridade. Reservar ou confirmar uma passagem de Revisor exige entrega `captured`. O módulo de checks abaixo consome essa versão e verifica ref/tree/base na materialização; revisão independente e publicação permanecem para suas sprints.

Provas locais: SQLite e filesystem reais com Git/canonicalização controlados; HTTP protegido, rollback, idempotência, recuperação de ref, persistência dos avisos sem bytes excluídos, modos, nomes com espaços/Unicode e parsing NUL de quebras de linha, diff paginado após remoção da implementação, conflitos e contenção. A medição AC-29 usa cache ignorado de 16 MiB e registra banco/WAL, metadados auxiliares, payload e latências em `SPEC_PROGRESS.md`. Objetos/ref Git reais, canonicalização integral neste sandbox, retenção após morte de runtime Git real e o percurso Maestri/OMP continuam pendentes no host autorizado. Fixtures não encerram AC-09/13/29 ou INT-18 integrais.

## Checks do controlador e evidências

`modules/verification/index.ts` oferece `createVerification({storage,workspaces,dataDirectory,logFailure})`, `verifyDelivery(deliveryId,signal)` e `getArtifact(artifactId)`. A composição de produção fornece verification ao pipeline; após confirmar a captura, o pipeline executa os checks capturados na tentativa. Declarações do Implementador não alimentam os resultados dos checks. A interface interna `pipeline.verifyDelivery` permite uma nova execução sobre a mesma versão, acompanhada pelo shutdown; não existe endpoint para enviar comandos ou executar checks livres.

`workspaces.materializeCheck(delivery,checkId)` confere ownership, ref direta, commit/tree/base e integridade dos objetos retidos. Reserva exclusivamente `<data>/work/<attemptId>/checks/<checkId>/checkout`; clona do repositório retido sem hardlinks/alternates e busca explicitamente a ref `refs/factory/deliveries/...`, pois o clone normal busca branches. Faz checkout do commit exato e verifica tree/estado limpo antes de devolver o ambiente. Nunca lê o clone de implementação para obter o conteúdo de um check; cada check tem ambiente próprio, inclusive em reexecuções. Recursos parciais ficam identificáveis pelo checkId e não são adotados, apagados ou resetados.

O comando é a expressão de shell autorizada na configuração capturada `{id,command,cwdRelative,timeoutMs?}`. O runner usa o shell normal da plataforma, cwd explícito, stdin fechado e ambiente limitado às variáveis operacionais de paths/usuário/locale, mais `CI=true/NO_COLOR=1`; não injeta tokens/provider/Git/Wire. Dependências e ferramentas necessárias ao check precisam estar disponíveis no host ou ser preparadas pelo próprio comando autorizado. O cwd deve existir dentro do checkout; caminhos absolutos/drive/ADS, `..`, `.git`, symlinks/junctions e redirecionamentos canônicos são recusados. Não há sandbox geral para código de projeto confiável.

Timeout padrão de 300.000 ms, substituível pelo timeout capturado, máximo 2.147.483.647 ms. Stdout/stderr são consumidos com teto agregado de 1 MiB; excesso é erro, sem sucesso truncado. Erro nativo ao lançar o shell recebe `CHECK_LAUNCH_FAILED`; close com zero é `passed` e código não zero é `failed`. Erro de um comando interpretado pelo shell conserva o exit code do shell. Timeout, cancelamento, sinal e output excedido são erros técnicos. Parada usa somente o processo próprio; matar o shell não comprova parada de seus descendentes. Esses casos conservam `STOP_UNCONFIRMED`, impedem checks posteriores e não autorizam limpeza do ambiente.

Migration 007 acrescenta `verification_runs`, `checks` e `artifacts` STRICT. A intenção e as definições por valor são confirmadas antes do IO. Cada execução recebe outro `runNumber`; FKs compostas vinculam tentativa, entrega, tree e rodada técnica. O histórico concluído é imutável. Check registra comando/cwd/timeout, IDs, versão, estado, exit code, início/fim, duração do processo, diagnóstico geral e `executionDiagnostic`. Este último conserva timeout/falha de processo mesmo quando a evidência também falha. Ausência de checks produz `not_applicable/CHECKS_NOT_CONFIGURED`, sem fabricar aprovação. Falhas suspendem a coordenação em `VERIFICATION_FAILED`; reinício marca intentos pendentes/running como erro interrompido. Verificação não declara entrega nem despacha revisão independente nesta sprint.

Somente logs pertinentes de checks são coletados. Valores sensíveis conhecidos do ambiente, headers de credenciais, URLs com senha e formatos conhecidos de token/chave são redigidos antes de gravar. Essa redação não é um detector universal de segredos em texto arbitrário. Não há varredura de projeto/caches, upload ou persistência de transcript/diff completo. O log fica em `<data>/artifacts/<attemptId>/<checkId>/<artifactId>.log`, permitindo localizar um arquivo órfão pelo check mesmo se a transação de metadados falhar. Gravação usa temporário exclusivo, sync, rename e conferência dos bytes antes da transação que confirma SHA-256/tamanho/vínculos e resultado. Nenhum IO de arquivo/processo ocorre sob SQL. Falha preserva diagnóstico, intentos e recursos; nunca confirma passed sem metadados da evidência. Não existe purge automático.

| Endpoint protegido | Conteúdo |
| --- | --- |
| `GET /api/v1/deliveries/:deliveryId` | Acrescenta `verification`: resumo da execução mais recente ou null; sem carregar logs/checkout. |
| `GET /api/v1/deliveries/:deliveryId/checks?limit=25&cursor=...` | Histórico por `runNumber DESC,id`, até 100 por página; cursor fixando versão e teto observado; checks e metadados de artefatos, sem bytes. |
| `GET /api/v1/artifacts/:artifactId` | Verifica escopo/vínculos, raiz canônica, arquivo regular, tamanho e checksum antes da resposta. `ARTIFACT_MISSING` (404) e `ARTIFACT_INTEGRITY_FAILED` (409) são explícitos. |

Artefatos são `text/plain`, `nosniff`, `attachment`, CSP restritiva e `no-store`; o nome de download é gerado pelo servidor. Não há parâmetro de path ou endpoint de upload. Consultas verificam novamente o escopo depois do IO.

Após o build, `npm run test:verification-compiled` executa checks Node reais de sucesso e reprovação, cwd/UTF-8 com espaços e Unicode, gravação/sync/rename e leitura com checksum, corrupção e ausência. Não executa Git/GH, Maestri ou providers. O resultado explicita se canonicalização precisou ser controlada por EPERM do sandbox; isso não substitui a prova de materialização Git no host autorizado.

## Revisão independente e correções limitadas

Após captura e checks concluídos, o pipeline registra revisão/passagem/terminal antes dos efeitos. Erro técnico ou parada incerta de check impede revisão; checks reprovados podem ser avaliados, mas impedem aprovação. Ausência de checks permanece `not_applicable`, sem fabricar sucesso. O Revisor recebe issue, critérios, versão, resultados dos checks e achados pendentes, sem conversa do Implementador. `workspaces.materializeReview(delivery,reviewId)` reserva `<data>/work/<attemptId>/reviews/<reviewId>/checkout` exclusivamente e materializa o mesmo commit/tree/base retidos dos checks. Recurso parcial não é adotado ou apagado. Cada revisão abre outra sessão Maestri/OMP e confere o perfil/recurso capturados; handshake rejeita sessão/terminal já usados por outra passagem viva.

Antes de aceitar o primeiro resultado revisor, `validateReviewerResult` na composição exige `workspaces.validateReview`. A verificação relê a ref retida, HEAD, status NUL e bytes de todos os blobs tracked, sem filtros, sem escrever objetos/índice e sem confiar em flags assume-unchanged/skip-worktree. Confere modos onde suportados e estabilidade das leituras; inclusões não ignoradas/staging/remoções/commits ou bytes divergentes invalidam o parecer. Caches ignored gerados ficam fora do produto. Falha de leitura/Git impede confirmação; invalidez já observada é permanente naquela revisão, mesmo se o checkout for reparado. Isso é conferência na entrega do parecer, sem bloqueio de filesystem ou vigilância contínua.

Migration 008 acrescenta `reviews`, `findings` e `finding_resolutions` STRICT, índices, FKs compostas e guards. Revisão registra versão, execução dos checks, passagem, estado, parecer declarado, motivo, independência/diagnóstico e tempos. `acceptResult` confirma resultado/recibo, critérios, achados e resoluções antes do ACK. Cada achado recebe UUID próprio, preservando também a chave declarada pelo Revisor, problema, evidência, resultado esperado e vínculos; categoria técnica é explícita, inclusive com `criterionIds:[]`. Revisão posterior recebe os UUIDs como `findingKey` das resoluções. Cobertura exata, ausência de duplicatas e vínculos à mesma tentativa são obrigatórios. Aprovação exige critérios passed, independência válida, nenhum impedimento novo e resolução independente dos anteriores; não resolve achados por declaração do Implementador. `declaredVerdict` distingue aprovação declarada de um parecer invalidado. Aprovação histórica move a fase a `publishing`, com resultado final nulo: o gate atual e os efeitos de publicação continuam necessários.

Reprovação registra a próxima rodada antes de enviar contexto estruturado. `execution.continuePassage(source,request)` usa somente a sessão viva do Implementador e seu cwd/perfil/recurso originais; não recruta outro terminal. A passagem nova tem identidade/resultado próprios e `session_source_id` imutável liga sua sessão à passagem anterior. Frame/ACK de continuação confirma o enfileiramento por `sendUserMessage(...,{deliverAs:'followUp'})`; timeout/perda fica diagnosticado e não reenvia cegamente. O campo opcional v1 `findingResponses` torna-se obrigatório, com IDs exatos, quando há achados na correção. Só o próximo Revisor resolve os achados.

Rodadas vão de 1 a `1 + correctionLimit`, padrão 2 correções, aceitando 0–5. Toda correção produz outro deliveryId/ref, captura, checks e sessão revisora. A última correção também é revisada. Esgotamento encerra `finished/rejected` e preserva pendências/resultados; pergunta humana não consome rodada. Perda da sessão implementadora mantém diagnóstico e histórico, sem substituta oculta. A desconexão de um Revisor já concluído não revoga uma correção posterior. Reinício interrompe trabalho incompleto, sem restaurar sessões ou agendar passagem. Contexto tem teto de 1000 achados pendentes e os limites de frame/tarefa existentes; excesso impede despacho, sem truncamento aprovável.

## Observação completa da fila Ready

Sem responsável, responsável alheio, múltiplos responsáveis, draft e PR recebem motivos específicos. Bloqueadores não invalidam as demais issues. A consulta aplica também os estados locais já existentes de automação/consumo/ocupação, sem alterá-los. Ready representa uma condição observada, independente da ordem temporal entre atribuição e Status.

Em seguida usa posição quando `useBoardPosition` está habilitado e a leitura fornece posição documentada; número crescente e ID desempatarão. Sem posição, o fallback para número/ID é explícito. Projetos são agrupados por ID; prioridades de campos de Projects diferentes não são comparadas. A consulta solicita `POSITION ASC` do Project, sem prometer a ordenação de uma view visual filtrada. Referência primária: [GitHub GraphQL Projects](https://docs.github.com/en/graphql/reference/projects#projectv2itemorderfield).

## PR, reconciliação e aumento de modo

O modo PR capturado autoriza o push necessário sem confirmação entre commit/push/PR. `workspaces.pushApproved` usa somente objetos retidos, valida tree/parent/mensagem/operação do commit local e envia um único refspec SHA→`refs/heads/factory/<issueNumber>/<attemptId>` para o HTTPS do repositório confirmado. Exige contexto Git com keyring e autorização de conta/repositório da composição confiável (`pushAuthorization`, derivada de `ControllerHostContext.githubMutationAuthorization`). Rejeita reescrita de URLs e transportes alternativos; conserva o credential helper normal do host. Confirma por `ls-remote --refs` com ref/SHA exatos. Branch remota divergente não é sobrescrita.

`github.mutateEffect` cria PR por GraphQL com repositórios head/base exatos, branch própria e base capturada. Consulta todas as páginas pertinentes antes e depois do envio. Confirma repositório, head/base, SHA, autor, marcador único, hash do corpo, título, estado aberto e URL; consulta também os refs atuais do head e da base. O corpo contém escopo, base/versão, checks/evidências, parecer, pendências não impeditivas e attemptId. Conteúdo editorial é tratado para impedir gatilhos de fechamento; não há merge, force-push ou edição de critérios. As releituras não oferecem CAS remoto: alteração concorrente após uma leitura pode produzir efeito incerto, que exige diagnóstico/reconciliação.

Intenção/claim são confirmados antes de cada mutação e o recibo antes da seguinte. O adapter GitHub chama a autorização novamente após as consultas prévias; cancelamento/restart invalidam a continuidade. Timeout enviado fica unknown até leitura confirmável. `reconcilePush` e `reconcilePullRequest` consultam os fatos conhecidos sem criar recursos; ausência, duplicidade, diferenças de identidade ou leitura parcial não autorizam replay. Confirmações tardias são registradas mesmo após cancelamento e não autorizam os próximos efeitos. Commit/push/PR sem delta recebem `not_applicable/APPROVED_NO_DELTA`, sem push ou PR vazia.

Migration 015 amplia os journals e adiciona `publication_upgrades`, imutável e vinculada a tentativa/versão/operação. O resumo oferece somente modos superiores para tentativa encerrada com versão corrente aprovada; o hash vincula revisões, configuração, versão/revisão técnica e estados dos efeitos. Autorizar valida retenção/evidências, gate atual, CAS e resumo antes da transação. A autorização adicional, recibo e evento são atômicos; a captura original e efeitos confirmados permanecem intactos. `authorizations.capturedMode` e `authorizedMode` são distintos. `complete` usa o modo já autorizado, sem exigir a confirmação adicional novamente, e `publication.localState` distingue conclusão do modo de um resultado anterior entregue.

Após restart não há conclusão automática nem restauração de sessão. A ação explícita exige recursos antigos reconciliados, gate atual e reconciliação dos efeitos. Falha conserva aprovação/refs/recibos; não reimplementa trabalho. Os contratos `publication.push`, `pullRequest` e `upgrades` apresentam estados, recibos, motivos e capacidades. Resumos não leem checkout, caches, diff ou bytes de logs; SQLite guarda somente referências/hashes/autorizações/estado. Provas locais de PR usam adapters controlados; AC-11/12/18/22 e INT-18 integrais ainda exigem alvos e efeitos reais autorizados.
